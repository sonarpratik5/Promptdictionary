## Acceptance criteria
| Area | Observable requirement |
| --- | --- |
| Discovery | Anonymous users find published prompts; URL filters survive refresh/back navigation; pagination has no duplicates; no matches has a useful empty state. |
| Adapt/copy | Substitution follows the agreed variable contract; stored templates remain unchanged; copied text matches the preview; clipboard failure is visible. |
| Share links | A shared link reopens a prompt with exactly the adaptation values it carries; it cannot introduce an undeclared variable, and its values are rendered as text only. |
| Contributions | Valid authenticated submissions persist; invalid inputs show actionable errors; owners can edit; non-owners and anonymous users cannot mutate them. |
| Privacy/moderation | Anonymous reads exclude unpublished content; direct database/API access cannot bypass ownership or role policies; moderation follows agreed transitions. |
| Bookmarks/feedback | User-specific state persists without duplicate records, including repeated requests; other users cannot alter it. |
| Content safety | Submitted markup/instructions remain inert content; no script execution, secret exposure, or automatic LLM calls. |
| Failure handling | Database/auth/network failures leave truthful UI state and allow recovery; failed saves never appear successful. |
| Accessibility | Core flows work by keyboard on mobile/desktop layouts with labels, visible focus, and understandable validation feedback. |

## Verification approach
- Vitest: deterministic validation and substitution edge cases after contracts are settled; test behavior, not implementation details.
- Integration: real isolated test database for constraints, RLS, ownership, publication visibility, and duplicate writes. Include anonymous, owner, another user, and moderator; mocks alone cannot verify policies.
- Playwright: browse → filter → detail → adapt → copy and authenticated submit/edit/bookmark flows, including meaningful failure cases.
- Run available lint, TypeScript checks, relevant tests, and production build for application changes. Use actual package scripts; do not invent commands before setup. Documentation-only edits need consistency checks, not application tests.
- Use deterministic synthetic fixtures; isolate users and clean up test data. Never run mutation tests against production.
- Performance targets: p75 LCP ≤2.5s, INP ≤200ms, CLS ≤0.1. Record route, device/network, dataset, and measurement method. Lab checks guide development; they do not establish field p75 results.
